# dataset_clips — 從教學長片挑出乾淨動作片段的工具

這些是 2026-08-14 擴充 `set`（14→24）與 `serve`（14→19）時實際用的腳本，原封保留下來
以便重用。它們**不是**自動化管線：中間一定要有一次人眼把關。

決策背景見 Obsidian `30-decisions/2026-08-14-volleyform-tutorial-clip-montage-gate.md`
與 `2026-08-04-volleyball-dataset-expansion-needs-human-labeling.md`。

## 流程

```
1. scan/locate  用 MediaPipe Pose 掃全片，找出候選窗口，輸出 JSON
2. montage      把每個候選的關鍵格拼成一張標註圖  ← 人眼在這裡把關
3. trim         只把人眼確認過的窗口用 cv2 切成 mp4，寫進 dataset/<action>/
4. build_reference.py 重算
5. 跑全套測試（11 後端 + 1 前端）——沒過就 git checkout 還原
```

每個腳本開頭都有常數（來源影片路徑、輸出路徑、接受清單、門檻），改那裡即可。
執行用專案的 venv：`.venv\Scripts\python.exe tools\dataset_clips\<script>.py`

## 檔案

| 檔案 | 用途 |
|---|---|
| `set_locate_windows.py` | 掃「雙手過頭且併攏」的舉球候選窗口 |
| `set_montage.py` | 舉球候選的把關圖 |
| `set_trim.py` | 切舉球片段（`ACCEPT` 清單在檔案上方） |
| `serve_scan_events.py` | 掃發球的過頭事件，記錄 elbow／above_nose／torso |
| `serve_verify_events.py` | 客觀檢查每個事件的**腳踝可見度**（腿有沒有入鏡） |
| `serve_montage.py` | 發球候選的把關圖（prep / contact / follow-through 三格） |
| `serve_trim.py` | 切發球片段（`WINDOWS` 清單在檔案上方） |
| `audit_contact_selection.py` | 稽核既有 dataset：contact 那一格有沒有第二個高度相近的候選 |

## 挑片時務必檢查的五件事

1. **關鍵瞬間要對得上系統的定義**。`serve`/`spike`/`block` 屬
   `phase_segmentation.OVERHEAD_ACTIONS`，contact 取「手腕最高的一格」。所以**下手發球
   不能混進 serve**——系統會把隨球動作當成擊球點。同理，沒有觸球的腳步練習片完全不能用。
   **拋球練習片同樣不能用，而且更危險**（2026-08-16 掃跳發球教學片時確認）：拋球到頂點
   時手臂又高又直，比真正擊球那一刻**還高還直**，contact 規則會直接選中它。混進去不是
   加雜訊，是把「擊球姿勢」教成拋球姿勢。
2. **伸展高度要除以軀幹長度，但一定要加上界**。直接用畫面座標比較，遠景的人會被系統性
   低估（所以要正規化）；然而手部特寫沒有軀幹，`torso` 會塌到 clamp，`above_nose / torso`
   反而爆到 5～7。

   > **`MAX_NORM = 1.5` 不是解剖學上界**（原本這樣寫是錯的）。純比例推算是 0.7，
   > 但**實測完整入鏡的發球到 0.95 就已經超過它**——分母是**影像投影**的肩到髖距離，
   > 軀幹後仰或斜角取景都會讓它縮短。1.5 的真正理由是**兩個 regime 差一個數量級**：
   > 正常 0.5-0.95、軀幹塌掉的特寫 5-7，1.5 落在中間的大空隙裡。它擋的是
   > **「分母失效」這個故障模式**，不是姿勢好壞的門檻。
   >
   > **這是硬過濾，不是排序護欄**：`norm >= MAX_NORM` 的影格在組 event 之前就被丟掉，
   > **不會進 montage，人眼看不到**。所以**上界設太低會靜默丟掉好片且無提示**。
   > 若遇到「明明有完整動作卻掃不到」，第一個懷疑這條。

3. **腿要在畫面內**。`serve`/`spike`/`block` 會取蹲踞期的膝蓋，腿被切掉會產生垃圾資料。
   用腳踝 `visibility > 0.5` 且 `y < 0.99` 客觀判斷，不要目測縮圖。
   **但這道 gate 會被騙**——畫面外的腿 MediaPipe 會直接幻覺出來還給高可見度，所以通過它
   只代表「通過啟發式」，**不等於全身真的完整入鏡**。第 2 點的上界因此是必要的，
   兩道一起用才有效（該片候選 342 → 100）。
4. **站姿發球和跳發球不要混**。目前 `serve` 的標準只描述站姿發球；`build_reference`
   把同一動作的所有片段**合成一條 band**（這點是確定的，code 就是這樣寫）。

   > **但「跳發球會被誤判」還沒被量過。** 常引的 90-105° 是**掃描器**的 2D 數字，
   > 跟後端門檻 108.3°（3D、取髖部最低格）**不是同一個量**，不能直接比。
   > **要動手之前先量**：拿一段真的跳發球跑一次後端，看膝角落在哪。
   > 若確實明顯低於現有站姿樣本，混進去就會「被 IQR 剔掉（等於沒補）」或
   > 「把站姿共用的下限一起拉低（等於放寬門檻）」，那時才需要子型感知的評估；
   > 若差距不大，這個顧慮可能根本不存在。

   `serve_scan_events.py` 會回報擊球前 1.6 秒內的最低膝角，但那**只是分流提示**：

   > 它跟後端的 108.3° **不是同一個量**，三處都不同——掃描器取「膝角最小的一格」的
   > **影像平面 2D 夾角**、固定回看 1.6 秒且取未平滑的最小值；後端 `_crouch_before`
   > 取「髖部最低的一格」（`max(hip_y)`）、用 `calculate_angle_3d` 的 **3D** 角、
   > 範圍是 contact 之前整段。**這些差異的誤差沒量過**，而站姿（約 110-150）與跳發
   > （約 90-105）最近的邊界只差 5°，很可能落在誤差裡。所以值偏低只是「值得看一下」，
   > 不能當判定。要知道某段會不會被誤判，得實際跑 `build_reference` 或評估流程。

5. **contact 取的是「全域」最高手腕**，所以要切成單一 rep，讓全域最高只涵蓋一次動作。
   查某個動作有沒有「兩個高度相近的候選」用
   `tools/dataset_clips/audit_contact_selection.py`。

   > 稽核**一定要用平滑後的訊號**（`_segment_overhead` 最小化的是 `_smooth()` 之後的
   > 序列）。2026-08-16 第一版用原始序列，得到的平手清單跟真的完全不同。
   >
   > 27 段 serve 的結果：差距 <0.01 的有 3 段——`pexels_6216953`（0.0012）、
   > `usertut_serve_10`（0.0052）、`pexels_6217332`（0.0067），其餘 24 段 0.014-0.126。
   > 注意 **`usertut_serve_10` 是切好的單 rep 短片也照樣近平手**，所以切片不保證不平手。
   >
   > 而且**差距大不代表選對了**：整段只有拋球沒有擊球的片子，最高峰也是唯一的。
   > 這個稽核只找得出「有兩個候選」，驗證正確性只能逐格看畫面。
